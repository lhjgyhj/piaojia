# 票夹（Piaojia）—— 需求开发报告（PRD）

> 版本：v1.0　日期：2026-11-09　作者：个人开发者
> 一句话定位：面向小团队的数电发票归集与报销查重系统。员工把 PDF、OFD、XML 发票上传或转发到专属收票邮箱，系统自动解析、查重、走报销审批，财务按公司模板导出。
> 技术栈：Django 5.2 LTS + Celery + PostgreSQL + Redis + HTMX。

---

## 1. 背景与行业痛点

### 1.1 数电票推广后，整理发票的工作量变大

全面数字化的电子发票（数电票）自 **2024 年 12 月 1 日**起在全国推广。同一张发票会同时存在 PDF、OFD、XML 三种文件，员工和财务都要人工收集、重命名、归档。

公开讨论里能看到具体数字：掘金上有财务相关文章提到，一家公司的财务每月要处理 800 到 1000 张 OFD 发票，作者帮同事整理过一个月的 217 张，原来都是逐张打开、复制金额。⚠️ 投简历前请自行打开原文核对。

### 1.2 重复报销是真实风险

数电票可以重复下载和打印，纸质时代"发票原件只能报一次"的约束不存在了。腾讯云社区有文章写道，要彻底防止重复报销，"会计还是得对收到的每张发票进行查重"；新浪上也有专门介绍"四大查重方式"的文章。⚠️

**但要讲清楚边界**：税务数字账户提供"入账标识"功能，企业可以在电子税务局把已入账的发票标记出来，这是防重复入账的官方手段（今日头条、会计学堂等有相关介绍）。所以本产品的定位不是替代税务系统，而是：

> 给**没有财务系统的小团队**，在**内部报销环节**做查重和流程管理。入账标识解决的是"这张票有没有入过账"，解决不了"这张票在我们公司有没有人报过"。

### 1.3 现有方案的缺口

| 方案 | 不足 |
|---|---|
| 票管大师、发票盒子等付费产品 | 功能完整但收费，数据存在对方服务器；小团队不愿意为几个人的需求付费 |
| 钉钉、飞书审批 | 有审批流，但没有发票解析和查重，附件还是靠人打开看 |
| 支付宝、微信发票管家 | 面向个人，不能做团队报销流程 |
| Excel | 手工录入、无法查重、多人协作容易覆盖 |

这些产品的存在说明有人愿意为这个需求付钱。个人开发者不需要做得比它们好，只要做成一个能用、能自部署的版本，并有真实用户。

## 2. 目标用户与使用场景

| 用户画像 | 规模 | 核心诉求 |
|---|---|---|
| 小公司财务兼行政 | 5~50 人，每月几十到几百张票 | 不用再逐张打开发票，自动汇总金额，防止重复报销 |
| 创业团队 | 没有专职财务 | 报销有记录、有审批、能导出给代理记账 |
| 代理记账的会计 | 服务多个小客户 | 按客户分开管理，月底批量导出 |

核心场景：

1. **S1 收票**：员工上传文件，或把发票邮件转发到团队专属地址，系统自动解析入库。
2. **S2 查重**：同一张票（同一发票号码）第二次进入系统时直接拒绝，并告知第一次是谁、什么时候提交的。
3. **S3 报销**：员工把若干张票组成一张报销单，填写事由，提交审批；审批人通过或驳回；财务标记已报销。
4. **S4 导出**：财务按月份导出 Excel 明细，并下载合并后的 PDF 存档。

## 3. 产品范围与版本规划

| 版本 | 时间 | 目标 | 交付物 |
|---|---|---|---|
| **MVP（v0.1）** | 第 1~4 周 | 上传三种格式、解析、查重、报销审批、Excel 导出 | 在线演示站 + GitHub 仓库 |
| **v0.2** | 第 5~6 周 | 专属收票邮箱自动收票、合并 PDF、统计看板 | docker-compose 一键部署 |
| **v0.3** | 第 7~8 周 | 多级审批、报销模板可配置、批量下载 | 真实团队试用 |

**明确不做**：

- **不爬国家税务总局发票查验平台**。那里有验证码，爬取违反其使用条款，也有合规风险。系统预留"查验结果"字段，由用户手动填写或后续对接正规接口。
- **不对接税局的入账标识接口**。需要企业的电子税务局授权，个人开发者做不了。
- **不做支付和收费**。个人备案网站不能做经营性业务；本产品免费，靠自部署版本获取用户。
- **不做 OCR**。数电票的 OFD 和 XML 都是结构化数据，PDF 里也有文本层。扫描件和拍照的发票不在范围内，文档里写清楚。

## 4. 功能需求

优先级：P0 = MVP 必须有，P1 = v0.2，P2 = v0.3。

### 4.1 账号与团队（F1）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F1.1 | 注册 / 登录 | 邮箱注册，激活邮件，找回密码 | P0 |
| F1.2 | 团队 | 注册时自动创建团队；所有数据按团队隔离 | P0 |
| F1.3 | 角色 | Owner（团队创建者）、Finance（财务）、Approver（审批人）、Member（普通员工） | P0 |
| F1.4 | 邀请 | 生成邀请链接，设置有效期和默认角色 | P0 |
| F1.5 | 审计日志 | 发票入库、报销单状态变化、成员变更全部记录操作人和时间 | P0 |

### 4.2 发票归集（F2）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F2.1 | 上传 | 支持 PDF、OFD、XML，单个 ≤ 10 MB，一次最多 20 个；拖拽上传 | P0 |
| F2.2 | 解析 | 提取发票号码、开票日期、金额、税额、价税合计、销售方、购买方、发票类型 | P0 |
| F2.3 | 解析结果确认 | 解析失败或字段缺失时，提示用户手工补录，而不是静默丢弃 | P0 |
| F2.4 | 专属收票邮箱 | 每个团队一个地址，如 `team-a1b2@发票域名`；员工转发邮件，系统自动提取附件入库，并回复处理结果 | P1 |
| F2.5 | 发票夹 | 列表、搜索（销售方、金额区间、日期区间）、按状态筛选 | P0 |
| F2.6 | 预览 | OFD 转图片或 PDF 后在线预览 | P1 |
| F2.7 | 购买方校验 | 团队设置自己的公司名称和税号，发票购买方不符时标红提醒 | P0 |

### 4.3 查重（F3）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F3.1 | 精确查重 | 同一团队内，发票号码唯一。重复提交时拒绝，并显示已有记录的提交人、时间和所在报销单 | P0 |
| F3.2 | 并发安全 | 两个人同时提交同一张票，数据库唯一约束保证只有一条成功 | P0 |
| F3.3 | 疑似重复 | 发票号码不同，但销售方、金额、开票日期都相同的，标记为"疑似重复"供人工判断 | P1 |
| F3.4 | 跨格式去重 | 同一张票的 PDF 和 OFD 分别上传，按发票号码识别为同一张 | P0 |

### 4.4 报销流程（F4）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F4.1 | 创建报销单 | 选择若干张"未报销"的发票，填写事由、费用类别 | P0 |
| F4.2 | 状态机 | 草稿 → 待审批 → 已通过 → 已报销；待审批 → 已驳回 → 草稿。状态只能按规则跳转，非法跳转返回错误 | P0 |
| F4.3 | 审批 | Approver 和 Finance 可以审批；驳回必须填写原因 | P0 |
| F4.4 | 标记已报销 | 只有 Finance 可以标记，表示钱已经打给员工 | P0 |
| F4.5 | 发票占用 | 一张发票同一时间只能在一张报销单里；报销单被驳回后发票释放 | P0 |
| F4.6 | 通知 | 状态变化时给相关人发邮件；群机器人通知（企业微信、钉钉、飞书） | P1 |
| F4.7 | 多级审批 | 按金额阈值走不同审批人，例如 1000 元以下一级、以上两级 | P2 |

### 4.5 导出与统计（F5）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F5.1 | Excel 导出 | 按月份或报销单导出明细：发票号码、日期、销售方、金额、税额、报销人、状态 | P0 |
| F5.2 | 合并 PDF | 把报销单里的发票按顺序合并成一个 PDF，方便打印存档 | P1 |
| F5.3 | 统计看板 | 本月报销总额、待审批数量、按费用类别和销售方的汇总 | P1 |
| F5.4 | 导出模板 | 字段和列顺序可配置，适配代理记账要求的格式 | P2 |

## 5. 核心业务规则

### 5.1 报销单状态机

```
  [草稿] ──提交──▶ [待审批] ──通过──▶ [已通过] ──财务确认──▶ [已报销]
     ▲                │
     └──驳回(填原因)──┘
```

- 每次状态变化在同一个数据库事务里完成三件事：更新报销单状态、写审计日志、更新发票占用状态。
- 已报销的单据不能再修改。需要更正时，财务执行"作废"，发票释放回发票夹，作废原因写入审计日志。
- 删除发票只允许在"未占用"状态，且是软删除，保留 30 天。

### 5.2 查重规则

- 主键：`(team_id, invoice_number)` 唯一约束。数电票发票号码为 20 位。
- 发票号码为空的文件（解析失败）不参与查重，进入"待确认"队列，由用户补录后再入库。
- 疑似重复不阻断提交，只在界面上显示警告。

## 6. 非功能需求

| 类别 | 指标 |
|---|---|
| 性能 | 单张发票解析 ≤ 2 秒；100 张批量上传在 1 分钟内完成（异步处理，前端显示进度） |
| 可靠性 | 解析任务失败自动重试 3 次；邮件接收幂等，同一封邮件重复投递不重复入库 |
| 安全 | 文件类型三重校验（扩展名、MIME、文件头魔数）；OFD 解压前检查压缩比和文件数，防止 zip 炸弹；单文件 10 MB、解压后总计 50 MB 上限 |
| 租户隔离 | 所有查询强制带团队过滤，有测试覆盖；A 团队用户访问 B 团队发票返回 404 |
| 隐私 | 发票可能含个人姓名。提供隐私政策、数据导出和账号注销（删除全部数据）；文件存储按团队分目录，下载链接带签名和过期时间 |
| 备份 | 数据库每日备份；发票原件和数据库一起备份，保留 30 天 |

## 7. 核心数据模型（概要）

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Team | name, slug, company_name, tax_id, inbound_address | 团队及公司信息 |
| Membership | user, team, role | 成员与角色 |
| Invoice | team, number, issue_date, amount, tax, total, seller_name, seller_tax_id, buyer_name, buyer_tax_id, type, status, file, sha256, parsed_from | 发票。`(team, number)` 唯一 |
| InvoiceFile | invoice, kind(pdf/ofd/xml), path, size | 同一张票的多个格式 |
| ExpenseReport | team, creator, title, category, total, status, submitted_at | 报销单 |
| ExpenseItem | report, invoice | 报销单与发票的关联。`invoice` 唯一，保证一张票只被一张单据占用 |
| ApprovalRecord | report, actor, action, comment, created_at | 审批记录 |
| InboundEmail | team, message_id(唯一), from_addr, received_at, status | 收到的邮件，用于幂等 |
| AuditLog | team, actor, action, object, diff, created_at | 审计日志 |

详细字段和约束见技术调研报告。

| 周 | 任务 | 验收标准 |

| 1 | 项目骨架、用户与团队、角色权限、Docker 开发环境 | 能注册、邀请成员、按角色看到不同菜单 |

## 9. 成功指标

- 注册团队数、真实发票数（剔除演示数据）、查重拦截次数。
- 至少 1 个非自己的团队持续使用一个月。
- GitHub star 数、docker 镜像拉取量。
- 简历表述示例："上线 X 个月，Y 个团队使用，累计归集 Z 张发票，拦截重复报销 N 次"。

推广渠道：掘金（写解析数电票的技术文章并附上项目）、V2EX、小红书（面向财务人员）、会计相关的微信群和论坛。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 数电票 XML / OFD 格式有多个版本，字段名不同 | 解析失败 | 解析器按版本分支，字段缺失时降级为手工补录；建立样本库做回归测试 |
| 真实发票样本难获取 | 无法验证解析器 | 用自己的发票；在文章里征集样本（脱敏后）；参考财政部《电子凭证会计数据标准》 |
| 财务人员不信任个人开发者的服务器 | 没有真实用户 | 主推 Docker 自部署，数据留在用户自己机器上；在线版只做演示 |
| 发票含个人信息 | 隐私合规 | 隐私政策、加密传输、签名下载链接、注销即删除 |
| OFD 是压缩包，可能是 zip 炸弹 | 安全 | 解压前校验压缩比、文件数量和总大小 |
| 个人备案不能收费 | 无法变现 | 不做收费功能，求职阶段以用户数和使用量为目标 |
| 邮件进垃圾箱或被退信 | 收票失败 | 配置 SPF、DKIM、DMARC；文档说明如何把收票地址加白名单 |
