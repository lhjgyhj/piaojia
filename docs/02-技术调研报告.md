---

## 1. 调研结论（TLDR）

- 技术栈：**Django 5.2 LTS + Celery 5.7 + PostgreSQL 17 + Redis + HTMX + Tailwind CSS**，Python 3.13。
- 解析器自己写，不依赖识别发票的第三方库：XML 用标准库解析，OFD 本质是 ZIP 包直接解压取 XML，PDF 用 `pdfminer.six` 提取文本层。
- 收票用**自建域名 + aiosmtpd**：给每个团队一个专属地址，用户转发邮件即可，不需要交出自己的邮箱授权码。
- 查重靠数据库唯一约束 `(team_id, invoice_number)`，不靠应用层判断。
- 报销流程用显式状态机，所有状态变化走同一个服务函数，保证审计日志和发票占用同步更新。

| pdfminer.six | 最新版 ⚠️ | 提取 PDF 文本层 |
| openpyxl | 3.1+ ⚠️ | 导出 Excel |

| aiosmtpd | 1.4.6（2024-05-18）✅ | 自建收信服务 |

### 2.2 为什么用 Django

发票报销是典型的业务系统：多角色、审批流、后台管理、大量表单和列表。Django 的优势正好覆盖这些：

- **ORM 和事务**：查重、发票占用、状态变化都要在一个事务里完成，Django 的事务装饰器足够用。
- **Admin**：运营后台不用自己写，可以直接查看团队、封禁账号、排查解析失败的发票。
- **权限**：`django.contrib.auth` 加自定义角色，比自己实现快。
- **模板**：报销单、审批页都是服务端渲染的表单，用 HTMX 做局部刷新即可，不需要前后端分离。

对比之下，证书监控项目改用了 FastAPI，因为它的核心负载是并发网络 IO。两个项目的技术选型理由不同，面试时可以对比着讲。

### 2.3 前端

**HTMX + Tailwind CSS + Alpine.js（少量）**。

- 上传进度、发票列表筛选、审批操作都是局部刷新，HTMX 够用。
- 不引入前端框架，把精力放在解析器和业务流程上。这是这个项目真正的难点。

## 3. 发票解析

### 3.1 三种格式的本质

| 格式 | 本质 | 解析方式 |
|---|---|---|
| XML | 数电票的结构化数据文件，字段完整 | 标准库 `xml.etree.ElementTree`，按命名空间和标签名提取 |
| OFD | ZIP 压缩包，里面是 XML 和资源文件（GB/T 33190） | `zipfile` 解压后解析其中的 XML |
| PDF | 版式文件，数电票的 PDF 有文本层 | `pdfminer.six` 提取文本，再用正则匹配字段 |

优先级：同一张票同时有多种格式时，以 XML 为准，OFD 次之，PDF 只作为补充。因为 PDF 文本提取受排版影响，最不可靠。

### 3.2 XML 字段（⚠️ 开工第一周用真实样本核对）

数电票 XML 的常见结构如下。不同版本的标签名可能不同，解析器要兼容多个版本：

```xml
<EInvoice>
  <Header>
    <EIid>发票号码（20 位）</EIid>
    <EInvoiceType>发票类型</EInvoiceType>
  </Header>
  <EInvoiceData>
    <SellerInformation>
      <SellerName>销售方名称</SellerName>
      <SellerIdNum>销售方税号</SellerIdNum>
    </SellerInformation>
    <BuyerInformation>
      <BuyerName>购买方名称</BuyerName>
      <BuyerIdNum>购买方税号</BuyerIdNum>
    </BuyerInformation>
    <BasicInformation>
      <TotalAmWithoutTax>不含税金额</TotalAmWithoutTax>
      <TotalTaxAm>税额</TotalTaxAm>
      <TotalTax-includedAmount>价税合计</TotalTax-includedAmount>
      <RequestTime>开票日期</RequestTime>
    </BasicInformation>
  </EInvoiceData>
  <TaxSupervisionInfo>
    <InvoiceNumber>发票号码</InvoiceNumber>
    <IssueTime>开票时间</IssueTime>
  </TaxSupervisionInfo>
</EInvoice>
```

这个结构是根据公开资料整理的，**没有逐字段核实**。开工第一周要做的第一件事：收集至少 10 张真实发票的 XML（自己的即可），把实际标签名整理成对照表，写进解析器的测试样本。

解析策略：

- 不假设固定的嵌套层级，用"标签名 → 字段"的映射表查找，找到第一个非空值即采用。
- 映射表按版本维护，例如 `{"发票号码": ["EIid", "InvoiceNumber"], ...}`。
- 金额统一用 `Decimal`，不用 `float`。
- 解析失败时保存原始文件和错误信息，进入"待确认"队列，不丢数据。

### 3.3 OFD 解析

```python
import zipfile
from decimal import Decimal

def parse_ofd(path: str) -> dict:
    with zipfile.ZipFile(path) as z:
        _check_zip_bomb(z)          # 见第 6 节
        # OFD 的发票数据在特定 XML 里，常见路径：
        # Doc_0/Attachs/ 下的原始 XML，或 Doc_0/Pages/ 下的内容描述
        names = z.namelist()
        xml_name = next(n for n in names if n.endswith(".xml") and "original" in n.lower())
        return parse_xml(z.read(xml_name))
```

OFD 内部结构在不同开票软件里不一样，有的把原始 XML 作为附件嵌入，有的只在版式描述里放文本。解析器按以下顺序尝试：

1. 找嵌入的原始 XML 附件，走 XML 解析。
2. 找不到时，提取版式 XML 里的文本节点，走和 PDF 一样的正则匹配。
3. 都失败则进入待确认队列。

`easyofd`（版本 20260427，Apache 许可 ✅）只用于把 OFD 转成图片做在线预览，不用于提取字段。字段提取自己写，避免依赖一个版本号是日期的库的内部实现。

### 3.4 PDF 解析

```python
from pdfminer.high_level import extract_text
import re

def parse_pdf(path: str) -> dict:
    text = extract_text(path)
    number = re.search(r"发票号码[:：\s]*(\d{20})", text)
    amount = re.search(r"价税合计.*?[¥￥]\s*([\d,.]+)", text, re.S)
    ...
```

- 只处理有文本层的 PDF。扫描件提取出来是空文本，直接提示"不支持扫描件，请上传 OFD 或 XML"。
- 正则按发票类型分别维护，每种类型用真实样本测试。
- PDF 解析结果标记 `confidence="low"`，界面上提示用户核对。

### 3.5 样本库与测试

建立 `tests/fixtures/invoices/` 目录，存放脱敏后的真实发票（金额和税号可保留，个人姓名替换）。每种格式、每种发票类型（电子普票、专票）至少 3 个样本。CI 里跑解析测试，字段不匹配即失败。

**这是这个项目最容易被面试官追问的部分**："你的解析器支持哪些版本？遇到新版本怎么办？"答案是：映射表驱动、解析失败不丢数据、有样本回归测试。

## 4. 收票邮箱

### 4.1 为什么不用 IMAP 拉取

让用户提供自己邮箱的授权码有两个问题：授权码等于邮箱密码，存在你的服务器上，泄露就是整个邮箱被读；用户也很难信任一个个人开发者保管自己的邮箱凭证。

改为**专属收票地址**：每个团队分配 `team-<随机串>@你的域名`，员工把发票邮件转发到这个地址。系统只收到用户主动转发的邮件，不接触用户的邮箱。

### 4.2 实现方案

| 组件 | 作用 |
|---|---|
| 域名 + DNS | MX 记录指向 VPS；配置 SPF、DKIM、DMARC，否则容易被退信 |
| aiosmtpd 1.4.6 ✅ | asyncio 的 SMTP 服务器，接收邮件后交给处理函数 |
| Celery 任务 | 解析附件、入库、回复处理结果 |

处理流程：

1. aiosmtpd 收到邮件，检查收件人是否是已分配的团队地址，不是则拒绝。
2. 用 `message_id` 做幂等：同一封邮件重复投递（SMTP 重试）不会重复入库。
3. 提取 PDF、OFD、XML 附件，交给解析器。
4. 回复一封邮件给发件人，说明每张发票的处理结果（已入库、重复、解析失败）。

### 4.3 备选方案

如果自建收信的到达率不理想（国内邮箱服务商对个人 VPS 的 IP 信任度低），可以改用 Cloudflare Email Routing：它的 Email Workers 能拿到原始 MIME 内容（入站上限 25 MiB ✅），再转发到你的 HTTP 接口。免费额度以官方文档为准，开工前确认。⚠️

### 4.4 安全

- 只接受已分配地址的邮件，其他一律拒绝，避免变成开放中继。
- 检查 SPF 和 DKIM 结果，不通过的邮件标记为"来源未验证"，不自动入库，等用户在界面上确认。
- 附件走和上传一样的文件校验。

## 5. 查重与状态机

### 5.1 查重

```python
from django.db import IntegrityError, transaction

def ingest(team, parsed, file):
    try:
        with transaction.atomic():
            invoice = Invoice.objects.create(team=team, number=parsed.number, ...)
            InvoiceFile.objects.create(invoice=invoice, file=file, kind=parsed.kind)
            AuditLog.objects.create(team=team, action="invoice.created", ...)
        return invoice
    except IntegrityError:
        existing = Invoice.objects.get(team=team, number=parsed.number)
        raise DuplicateInvoice(existing)
```

- 唯一约束在数据库层，应用层的"先查询再插入"在并发下会漏掉重复。
- 同一张票的第二种格式上传时，不新建发票，而是给已有发票追加 `InvoiceFile`。

### 5.2 状态机

```python
TRANSITIONS = {
    "draft":     {"submit": "pending"},
    "pending":   {"approve": "approved", "reject": "draft"},
    "approved":  {"reimburse": "reimbursed", "void": "draft"},
    "reimbursed": {"void": "voided"},
}

@transaction.atomic
def transit(report, action, actor, comment=""):
    new_status = TRANSITIONS[report.status].get(action)
    if new_status is None:
        raise IllegalTransition(report.status, action)
    report.status = new_status
    report.save(update_fields=["status"])
    ApprovalRecord.objects.create(report=report, actor=actor, action=action, comment=comment)
    _update_invoice_locks(report, new_status)
```

- 所有状态变化只走这一个函数，视图层不直接改 `status`。
- 驳回和作废必须有 `comment`，在函数里校验。
- 发票占用：报销单进入 `pending` 时锁定发票，回到 `draft` 或作废时释放。锁定用 `ExpenseItem.invoice` 的唯一约束实现，一张票不能同时在两张单据里。

## 6. 安全设计

| 威胁 | 对策 |
|---|---|
| 恶意文件上传 | 扩展名、MIME、文件头三重校验；只允许 PDF、OFD、XML |
| zip 炸弹（OFD 是压缩包） | 解压前检查：压缩比 ≤ 100、文件数 ≤ 50、解压后总大小 ≤ 50 MB；用 `zipfile` 逐个读取并累计大小，超限立即中断 |
| 路径穿越 | 解压时校验文件名不含 `..`，只提取预期的 XML |
| XXE（XML 外部实体注入） | 用 `defusedxml` 解析，不用标准库直接解析不可信 XML |
| 越权访问 | 所有查询带 `team_id` 过滤；文件下载走签名 URL，不直接暴露存储路径 |
| 租户隔离 | 参数化测试遍历所有视图，用其他团队的用户访问，断言 404 |
| CSRF、XSS | Django 默认防护；上传的文件不在页面里直接渲染为 HTML |
| 隐私 | 传输全程 HTTPS；数据库备份加密；账号注销时删除发票文件和数据库记录 |

## 7. 异步任务

用 Celery 5.7，任务包括：

| 任务 | 触发 | 说明 |
|---|---|---|
| 解析发票 | 上传后、收到邮件后 | 失败重试 3 次，仍失败则标记待确认 |
| 发送通知 | 报销单状态变化 | 邮件通知相关人 |
| OFD 转图片 | 用户第一次预览时 | 转换结果缓存，不重复转 |
| 合并 PDF | 用户点击导出时 | 大文件时异步生成，完成后通知下载 |
| 每日统计 | beat 定时 | 给财务发本周待审批汇总（P1） |

任务幂等：解析任务以文件哈希为键，重复执行不重复入库。

## 8. 数据模型补充

- `Invoice`：唯一约束 `(team_id, number)`；索引 `(team_id, issue_date)`、`(team_id, status)`。
- `InvoiceFile`：`sha256` 在团队内唯一，防止同一文件重复上传。
- `ExpenseItem`：`invoice_id` 唯一，保证一张票只被一张报销单占用。
- `InboundEmail`：`message_id` 唯一，保证邮件幂等。
- `AuditLog`：只插入不更新，应用层不提供删除接口。
- 金额字段全部用 `DecimalField(max_digits=14, decimal_places=2)`。
- 发票原件存在本地磁盘或对象存储，数据库只存路径。自部署版默认本地磁盘，按 `team_id/年/月/` 分目录。

```
                ┌── Caddy（自动 HTTPS，反代）
```

- 每日备份数据库和发票文件目录，保留 30 天。

## 11. 被否决的方案

| 方案 | 否决原因 |
|---|---|
| FastAPI | 这个项目的核心是业务流程和数据一致性，不是并发 IO；Django 的 ORM、Admin、权限更合适 |
| IMAP 拉取用户邮箱 | 需要用户交出邮箱授权码，安全风险和信任问题都大 |
| 爬税局查验平台 | 有验证码，违反使用条款，有合规风险 |
| OCR（PaddleOCR 等） | 数电票是结构化数据，不需要 OCR；引入 OCR 会大幅增加部署复杂度 |
| 用 easyofd 提取字段 | 库的版本号是日期，内部实现可能变化；字段提取是核心逻辑，自己写更可控 |
| 前端用 Vue 或 React | 交互复杂度不匹配，精力和难点应该放在解析器和业务流程上 |
